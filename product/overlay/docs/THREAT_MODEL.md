# Threat model (phase 1, rootmark 0.1.0)

Status: the P1-E/E5 release document; its source is `docs/SECURITY.md` (P1-D.1/D1.0, K-D1.3) with the additions of P1-E. The two documents are updated together. (This is the English translation; the Turkish original and `docs/SECURITY.md` are in the development repository, [arknsensei/rootmark](https://github.com/arknsensei/rootmark/blob/v0.4.0/docs/THREAT_MODEL.md).) Scope: `rootmark serve` (MCP stdio + 127.0.0.1 HTTP) and the `rootmark` CLI running on one machine over one user's vault. Multi-user servers, remote access and encryption at rest are phase 2 (ROADMAP P2-D).

## Assets
- The Markdown files (the single source of truth) and `.rootmark/` derived from them (event log, objects, checkpoints, traces, index).
- Provenance: who wrote each block, the actor of every layer transition and of every delete/change (K-D1.2).
- The integrity of `canonical` content: nothing a human has not approved counts as knowledge (NORTH_STAR).

## Trust boundaries and channels (K-D1.3)
| Channel | Authentication | Actor | What it can do |
|---|---|---|---|
| MCP stdio (`rootmark serve --mcp stdio`) | the client that starts the process; identity `initialize.clientInfo` | always `agent`, `id` = the client identity `<clientInfo.name>/<clientInfo.version>` (K-D1.3's "client name"; the P1-D ASSUMPTIONS D1-1 form) | reads, trace-writing reads, `propose` (under the EditPolicy), `checkpoint`; `promote` → `denied` |
| HTTP 127.0.0.1 (`--http`) | `Authorization: Bearer <.rootmark/server.token>` | `human:<policy.toml [identity] human_id>` | everything MCP can do + `promote` (allowed with `HumanOnly`); without `human_id` the write endpoints answer 403 |
| CLI `rootmark` | the local user's file permissions | stated explicitly in the command (`--actor human:<id>`); `rootmark propose` is an agent | everything; the policy hooks still apply |
| File watcher (`--watch`) | anyone who can write to the file system; the attestation of a human-channel client (P2-0, spec 2.0.0 §7.1) | an attested edit is `human`; with `[attestation] unattested = "unverified"` (optional; the default of spec 2.0.3 §7.1 is `canonical`, the reference kernel reads an old recipe without the table as `unverified`) an unattested edit is `unattested_fs`; the recipe `rootmark serve` writes has the value `canonical` (P2-A/A0, K-P2-02.5): every edit is `human` (the 1.0.3 behaviour) | takes attested md changes in as human content (`canonical`) and, when `unverified` is chosen, unattested ones as `unverified`; the definition and limits of the human channel are below ("Attested writes and the human channel") |

- `X-Consumer` is only a trace label (`traces.jsonl` `consumer`). It cannot change the actor kind: `X-Consumer: human:me` does not make an MCP/HTTP call human; the token does.
- **Accepted assumption:** every local process that can read the token file (`.rootmark/server.token`, mode 600) counts as the human. An agent process running under the same user account can move to the human channel if it can read the token. The keychain (stage 2) closes only the path of reading the token file; other ways into the human channel (driving Obsidian over CDP, writing the plugin's files) stay open — against a deliberate agent the only separation is a separate user account or a sandbox (below, "Attested writes and the human channel"). Recommended operation: run the agent in an account or a sandbox that cannot read the vault's `.rootmark/` directory, over MCP only.
- **The default policy is `canonical` (P2-A/A0; K-P2-02.5 (1), option (b)).** The `policy.toml` that `rootmark serve` writes into a vault without a recipe carries the line `[attestation] unattested = "canonical"` explicitly, and `status.attestation.unattested` says so: in new installations a write by a process that writes the vault's files directly counts as human (the 1.0.3 behaviour). When `unattested = "unverified"` is chosen (the default of spec §7.1 and of the kernel when there is no `[attestation]` table), an unattested write is taken in as `unverified` and its actor is `unattested_fs`; if the writing process is on the human channel (can produce an attestation) it counts as human. This distinction is the measured condition (NORTH_STAR, "measured condition"). Giving an agent write access to the file system outside MCP therefore reduces the "who" of provenance to "an unattested file write".

## Attested writes and the human channel (P2-0, P2-0.1, P2-0.2; spec 2.0.2 §7.1)
- **Stage 1 (active, `status.attestation.stage = 1`).** When `unattested = "unverified"` is chosen, rootmark does not count a process that writes the vault's files directly as the human: every unattested external change is taken in as `unverified`, its actor is `unattested_fs`, it is invisible to search by default and is not knowledge until a human promotes it. An attestation is a declaration of bytes coming from the human channel (`POST /v1/attest`, a MAC of the session key; MCP has no attestation).
- **The human channel** (P2-0 verification, recommendation 2, K-P2-01.1): the human channel is a write that goes through the Obsidian process (the plugin's observation of `adapter.write/append/rename/process`; other plugins in the same process are on this channel too) and the declaration of whoever runs the `rootmark attest` CLI. **Every local process that can start this process, drive it with a debugger (`--remote-debugging-port`, CDP) or write the plugin's files (`.obsidian/plugins/**`) is on the human channel** — this is a **path demonstrated** in P2-0's independent verification: the agent text written with `app.vault.adapter.write` over CDP into an Obsidian started from a terminal with a separate data directory and `--remote-debugging-port` was attested by the plugin (3/3 `canonical`; neither the token nor the keychain was touched; `reports/rounds/P2-0/VERIFICATION.md` V5). At stage 1 every process that can read `.rootmark/server.token` is on the human channel too (it can open a session and produce attestations). Stage 1 therefore separates a careless or instruction-following agent from `canonical`; it does not separate a deliberate agent running with its own user's permissions.
- **The limit of stage 2.** A keychain ACL (stage 2, not measured) trusts the application, not whoever drives it: moving the secret into the keychain closes neither the CDP path nor writing the plugin's files. Against a deliberate agent the separation comes only from an OS-level separation (a separate user account, a sandbox); this is outside the scope of P2-0 and P2-0.1 (GOAL P2-0.1, "Not done"). The plugin not attesting under a debugger is a separate decision (the harness uses CDP).
- **Rename and link update (P2-0.1, K-P2-01.2).** The link updates Obsidian writes during a rename are attested with `link_update_of`; the server accepts only the bytes where link targets naming the renamed note (and its old path) changed, in the live `canonical` blocks of the head (in the late case, the head before the pending unattested change); otherwise 403 `denied`. An attestation matches at most one change; an unattested ingest voids the document's earlier attestations. Known limits: a folder rename's link updates are not attested (`unverified`); an agent can drop a human's pending attestation with a single unattested write (availability, not laundering); in a rename whose old path is unknown, a narrow race can point the target of a `canonical` link to the renamed note (prose is not carried; ASSUMPTIONS P2-0.1 Y1-3).
- **Link forms and carrying layers through a rename (P2-0.2, K-P2-02.2).** The label of a Markdown link whose target changed may only turn from the old target's name into the same form of the new target's; every other difference is still 403 `denied`. A rename (`renamed_from`) and the renamed note's own link update no longer require "all `canonical`": the bytes must be the head of the old path (at most with the note's own links rewritten) and each block carries its layer on the old path as it is — `unverified` stays `unverified`, `proposal` stays `proposal`, no block is raised (a `proposal` of `human` origin is carried as `unverified`: lower). So unattested content an agent wrote into a note stays `unverified` even if the human renames that note in Obsidian; an observation that matches a ceilinged attestation whose ceiling cannot be found is taken in as unattested (fail closed). In the link update of other notes the changed block must still be `canonical` (F6 below). `link_update_from` is used only when the old file is not on disk (a copy is not a rename); the token holder can imitate a rename (the "process that can read the token" class) but cannot add content.
- **Concurrent writes (P2-0.1, K-P2-01.3).** If the human's save and the agent's write fall into one observation of the watcher, an attestation carrying the saved bytes (`content`) vouches only for its own blocks (a partial match): the human's blocks are `canonical`, the agent's `unverified`. If the attestation carries no `content` (an older client) the whole observation stays `unverified` (the safe side). Obsidian merging an agent's not-yet-observed change into the editor and saving it makes those bytes attested too (P2-0 Z3 finding 12; an open limit).
- **Known limits (P2-0.1 verification F6, F7; K-P2-01.6).** (F6, safe side) A link update is checked as a whole: if the note Obsidian rewrote holds a linked agent block or agent bytes not yet taken in, the link update is refused and the human's link paragraph in the same note stays `unverified` too (availability, not laundering; the human promotes). (F7, the "process that can read the token" class) A process that reads the token can make its own block `canonical` with a full hash as well as with a partial match carrying `content`; this is not a new path, it is stage 1's accepted assumption.
- **An unmatched attestation (P2-0 verification F5).** An attestation is not refused (it can come before the write); if at the moment it is recorded the file does not hold those bytes (or, if it came with `content`, their blocks), it has no late match and the window holds no pending change of those bytes, it goes into the log with `matched: false`; an attestation that matches later keeps this mark. `status.attestation.unmatched` counts the rows "not matched at the moment they were recorded", not "never matched".
- **The close of the P2-0 series (P2-A/A0; K-P2-02.5 (2), (5)).** (A) The renamed note's own late link update — when the watcher first sees the note at its new path with its links rewritten (the path is new to the log) — is now checked, as spec §7.1 says, **against the head of the old path** (from the accepted rename attestation or from a `link_update_from` whose file is not on disk); before, it was checked against the empty head before that ingest and refused (P2-0.2 FINAL note 3). The check stays the same: a byte not in the old head (a paragraph an agent added) makes the link update `denied` and nothing is raised. **Diagnostic log:** `rootmark serve --attest-log <file>` (outside the vault only; a path inside the vault is refused at start) writes every attestation call (accepted / refused, code and reason) and every observation (the `seq` distance of an attested match; for an unattested observation, the same document's unmatched accepted attestations and why: `other_bytes`, `expired`, `consumed`); no decision reads it. The log carries document paths and content hashes (not content). **Known limits (P2-0.2 verification):** (F2) the value of 0.2b depends strongly on timing and load (116–297/2743 on the same commit); in an installation that chooses `unverified`, the rate of wrong `unverified` varies with the environment. (F3) `renamed_from` is accepted while the old file is still on disk (a copy); there is no raise (the carrying rule), it is within the limit "a process that can read the token can imitate, cannot add content". (F4) A human's attested edit does not raise a block that stayed `unverified` (spec §7 layer inheritance): a paragraph that dropped once is not recovered by editing it; it needs a promotion. (F5) Two `rootmark serve --watch` can run on the same vault at once, and when both write, `events.jsonl` is corrupted (no lock); the user must run one server. (F6) The link paragraph in a side note can stay `unverified` in the side note too if the renamed note carries `unverified` content or its update was refused (cascading, safe side; availability); a Markdown link with a folder path (`md_path`) could not be measured with Obsidian's `shortest` setting.
- **The limit of the P2-0 series (P2-0.3, K-P2-03.1; P2-L/L0 a, b).** The default `canonical` is final; `unverified` is optional and stays with its measured behaviour: the content of an agent that writes the file directly does not count as `canonical` (leakage 0); a share of the human's own edits stays `unverified` in renames, **depending on a race** — not systematically: on P2-0.3's official seed 151/2228 = 0.0678, 140 of them one event (35 blocks of the large self-linked `espresso` note; counted again in the next three renames because the layer is carried, seen in five of six chains), 0.0112 with 25 distinct blocks in the chain without the event; the main class is side notes whose incoming links Obsidian rewrites when a large note is renamed (`reports/rounds/P2-0.3/VERIFICATION.md`). A block that dropped once is not recovered by editing, it needs a promotion (F4). **The explained drop (P2-0.3 verification Ö3, P2-L/L0 b):** the `canonical` → `unverified` drop in observation 5 of the verification's V3 was a bug: when a note was renamed back to a path it held before (the watcher does not take deletes in, the log keeps the old head of that path), the note's own link update was checked against that old head and refused, the rewritten bytes were taken in unattested and the block in between dropped; now, if that check stays, it is made against the head of the accepted rename's old path (when its file is not on disk) (spec 2.0.3 §7.1). The reproduction and the run after the fix, with `--attest-log`, are in `reports/rounds/P2-L/l0_b/`; what remains `unverified` is the side-note class.


- **The headless human channel (P2-P/P3; K-Q.1 (7)).** A bot process that holds the token (e.g. a Telegram bot relaying a remote human's approval) **is the human channel**: it can `promote`/`demote` (and, if it wants, `propose`, `checkpoint`, attest) in the name of `[identity] human_id`. Therefore: (1) the bot must run in an **OS user account separate** from the agent processes; (2) the token file (`.rootmark/server.token`) must be readable only by that account (and the account running `rootmark serve`), and the agent account must not be able to read it (otherwise the agent is on the human channel too, the "process that can read the token" class); (3) the bot only relays the remote human's explicit approval (`history` → approval → `promote`), it decides nothing itself; (4) the bot sends `X-Consumer: <bot name>` and every promotion/demotion event carries it as `meta.source` (spec 2.0.3 §7): afterwards one can see through which channel something was approved. `human_id` is that human's identity; one recipe or one server per bot. **Open limit:** there is one `human_id` per server — if several humans approve through the same bot the events do not tell them apart (the label tells the channel, not the person); multiple identities go to P2-E. There is no remote access (other than 127.0.0.1): the bot runs on the same machine as the server. Setup and flow: `docs/HEADLESS_CHANNEL.md` (development repository).

## Governance guarantees
- **Promotion** (spec §7, K12/K16): the kernel does not decide; the `policy.toml [promotion]` hook decides. Promotion from MCP is always `denied`.
- **Declarative promotion rules (P2-P/P1, P2; K-Q.1 (2)).** `[[promotion.rules]]` makes an agent's `propose` directly `canonical` if its actor (`agent:<id>`, exact match), its source (optional, exact) and its path (prefix) match; the kernel still does not decide (the matcher is in `server`, `Promoted` comes from the kernel's hook). Guarantees (pre-registered security cases S1–S7, `server/tests/promotion_rules.rs`): **an unattested file write (`unattested_fs`) and `unverified` content are promoted by no rule** — the matcher runs only on a `propose` call and looks only at the `proposal` lineages that call wrote (whose version is new in that call); an external change taken in by the watcher, a late attestation (including a lineage that turns back into `proposal`) and a manual `promote` do not run it (S1, S4). A rule cannot be written for `human:…`, `policy:…` or `unattested_fs` (refused at load, S2); a path outside the prefix is not promoted (S3); a write `append_only` refuses writes nothing and is not promoted (S5); with a recipe without rules the behaviour and `events_hash` are unchanged, and with a recipe with rules the change of the default search is only in documents inside the prefix (S6); the rule's identity and `policy_version` are in `history`, and the human undoes it with `demote` (HTTP, `human_id`) (S7). **Open limit (security review, P2-P/P1):** the rule's actor is the name the client **declares itself** — `clientInfo.name` of `initialize` over MCP, `rootmark propose --source` on the CLI (K-D1.3: MCP is the agent channel and has no authentication). Every process that can talk to the server over MCP (can start the stdio process) or run `rootmark propose` can declare a rule's agent name and write `canonical` content under that rule's prefix. A rule therefore does not say "this name is this agent", it says "those who can run agents on this machine can write knowledge directly under this prefix"; the trust boundary is the OS account that runs the agent (the same level as the token assumption). Recommended operation: keep the rule's prefix narrow, set `source` too, and in a vault with rules run agent processes only with the expected clients; an authenticated agent identity (a key per client) goes to P2-E with multiple identities. Every block promoted by a rule shows its rule in `history` and the human undoes it with `demote`.
- **Agent writes** (K-D1.1): the default is `[edit] policy = "append_only"`. Every agent write that touches a canonical block (deletes, changes, moves, splits, merges it, or lowers its layer) or changes a canonical search unit (chunk) is `denied`. `unrestricted` applies only if written explicitly; even then every delete/change event carries its actor (K-D1.2).
- **Order** (K-D1.4): writing and trace-writing calls pass through one FIFO queue per vault. The same sequence of requests produces the same log.
- **No silent failure**: every refused call returns a stable error code (K-D1.5, `docs/CLIENT_CONTRACT.md`). A refused write writes nothing to the md files or to `events.jsonl`.
- **Retention and pruning (P2-R/R1, R2; CLIENT_CONTRACT §2.10).** Pruning is an **operator action**: it runs only with `rootmark prune <vault>` (a local user with write permission on the vault) or `POST /v1/prune` (the human channel: token + `[identity] human_id`, otherwise 403); it does not exist over MCP (an agent cannot prune) and `rootmark serve` does not prune by itself (`server/tests/p2_r_r2.rs` long-session test). Its decision is the recipe (`[[prune.rules]]`, `[retention]`) and derives only from the log, the checkpoint order and the recipe: changing the clock does not change a trace/checkpoint/position decision (only the pruning of the raw journal reads `now_ms`). A rule cannot prune `canonical` (the loader refuses `layer = "canonical"`, the kernel refuses pruning `canonical`); `unverified` only by a rule for that layer; a rule's `path_prefix` is vault-relative and NFC (a prefix that addresses outside the vault, or an NFD prefix, is refused at load). A pruned lineage only becomes `inactive` (spec §7, no object is deleted); at a checkpoint before the prune, `at` returns the earlier answer unchanged. The **archive** (`.rootmark/traces/archive/`, `.rootmark/checkpoints/archive/`, `.rootmark/traces/base`) is inside the vault and at the same trust level as write permission on `.rootmark`: a process with that permission can change the archive or `base`, just as it can change `events.jsonl`. Corruption is not silent: a malformed `base` or one that disagrees with the archive, a missing/extra archive file, live traces' `at_seq` not starting at `base`, a checkpoint file found in two places or in none make the vault fail to open and name the file; a change to an archived trace line is an error in `rootmark trace list --archived` (`at_seq`, the `trace_id` formula). `dry_run` changes no file. rootmark does not delete the archive; `events.jsonl`, `objects/`, `snapshots/`, `attestations.jsonl` are never pruned. Pruning with the CLI while the server runs is not ordered with it, like other CLI writes (below, "Concurrent writer outside the server"), and worse, because the CLI changes `traces.jsonl` by renaming it, a trace line the server appends at the same moment can be lost: if the server runs, use `POST /v1/prune` (it goes through the queue). A prune cut short can leave the vault unable to open (the archive written, `base` not written); the files are written synced, the repair is in CLIENT_CONTRACT §2.10. `now_ms` is not bounded: the token holder can shorten the raw journal's 24-hour lower bound for that call with a future time (the existing behaviour of `journal prune --now-ms`; an unversioned record is not deleted). An agent can keep the prefix of the trace archive (and that checkpoint) alive by querying an old checkpoint it read with `at` again and again: the volume grows, nothing is deleted or answered wrongly (ASSUMPTIONS R2-2).

## Network
- HTTP binds only to `127.0.0.1`; every other address (IPv6 loopback included) is refused before start.
- The `Host` header is not checked. A request from a browser through DNS rebinding gets 401 because it does not know the token. As long as the token stays secret, neither reads nor writes are possible.
- The token is 64 hex (256 bits), compared in constant time, and rotates with `[server] token_rotate_days`.

## Client (P1-E)
- The Obsidian client (`clients/obsidian`) speaks only the HTTP contract: it reads the token file and `policy.toml [server] http_port` read-only, does not write md files (static scan + the E-3 watcher), and does not start `rootmark serve`. A plugin that can read the token is on the human channel (the same trust level as the accepted assumption).
- **The VS Code skeleton (P2-B/B4 (b)).** `clients/vscode` speaks the same HTTP contract (`X-Consumer: vscode`); it reads the token from the vault's `.rootmark/server.token` read-only on every connect and keeps it **in memory only** — it writes it to no setting, `globalState`, `SecretStorage`, workspace or log; it does not write md and does not start `rootmark serve`. A plugin that can read the token is on the human channel, like the Obsidian plugin. **It does not attest saves:** a VS Code save is an unattested external change seen by the watcher (if `unattested = "unverified"` is chosen the blocks become `unverified`, actor `unattested_fs`); this is the same as a save by any editor or script and does not make VS Code an additional attestation path into the human channel (`clients/vscode/README.md`). The position (`loc`) is for reading only: the client writes nothing with a position; promotion and demotion still go through the `promote`/`demote` endpoints and the policy.
- The client shows an answer outside the contract or malformed as `bad_response` and does not accept it silently; it does not show proposal results unasked, nor hide them.

## Known open limits
- **The temporary directories of `rootmark conformance`:** the binary's own working directory is randomly named, exclusive and 0700; but the frozen conformance evaluators compiled into it (`core/tests/conformance/eval*.rs`, `index/tests/conformance/eval_c3.rs`) set up their case directories with predictable names (`$TMPDIR/rootmark-conf*-<pid>-<n>-…`) and first delete what is there. On a shared machine another local user can create these paths beforehand (symlinks included) and mislead or break the command. Mitigation: run `rootmark conformance` with a personal `TMPDIR` (on macOS the default `TMPDIR` is already per user; on Linux `TMPDIR=$(mktemp -d)`). The evaluators are frozen measurement code; the fix comes with a phase 2 freeze exception.
- **TOCTOU (K-D4-T c):** between `propose`'s path check and its write, another local process with write permission on the vault can replace a directory with a symlink. Closing it fully needs an `openat`/`O_NOFOLLOW` chain (phase 2).
- **Case-insensitive file systems:** a new document can be created under a name differing only in case from a document whose file was deleted; provenance stays correct. (K-GH.6, P2-A/A4) `propose`'s refusal of spelling variants folds NFC + lower case, not full Unicode case folding: pairs like `ſ`/`s`, `ς`/`σ` are caught on macOS by the operating system's check (fail closed); on Linux `ſub/b.md` can open a second directory beside `sub/` (portability, not security).
- **The CLI's actor is declared:** `rootmark promote --actor human:<id>` is the declaration of the person who runs the command; every process that can run the CLI can declare a human. This is the same trust level as the token file assumption.
- **Link reference definitions:** an agent can add a Markdown link reference definition (`[name]: url`) to its own headed section. This can change the displayed link target of a canonical block using the same name. The block's text, provenance and search units do not change (`append_only` measures this). Clients should not apply reference definitions from proposal blocks to canonical blocks.
- **A concurrent writer outside the server:** writing to the same vault with the CLI while the server runs is not locked in the kernel (ASSUMPTIONS P1-D D1-3). The single writer queue orders only the server's calls.
