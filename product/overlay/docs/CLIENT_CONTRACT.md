# The rootmark client contract (P1-D.1, K-D1.5; P1-E/E0 K-E0.3, K-E0.4; P1-E.1 K-E1.2; P2-0 K-P2-0.4, K-P2-0.5; P2-B K-P2B.1 — version 2)

Status: **version 2** (P2-B: block position `loc`/`loc_stale` §2.5, the date filter §2.2, the event stream §2.8, the machine-readable response schema §2.9; the spec is unchanged). Every field of version 1 stays as it is, the fields of version 2 are optional: a version 1 client does not break, and a version 2 client talking to a version 1 server reads a missing field as "absent" (§6). This document is the **whole** of the P1-E client's (and every MCP/HTTP client's) dependency on `rootmark serve`. A client relies on no behaviour that is not written here. Every tool and every error code of the contract is matched by at least one test, and every §1 endpoint and §3 status row by a real HTTP call (`scripts/contract_check.sh`). For the spec's concepts see `spec/SPEC.md`; for the security model, `docs/SECURITY.md` (development repository) and [docs/THREAT_MODEL.md](THREAT_MODEL.md). (This is the English translation of the Turkish original in the development repository; the code spans, the table keys and the schema block are the original's, byte for byte.)

## 1. Transports and channel → actor (K-D1.3)
| Transport | Start | Identity | Actor |
|---|---|---|---|
| MCP stdio | `rootmark serve --vault <v> --mcp stdio` | `initialize.params.clientInfo` → consumer `<name>/<version>` (if empty, the trace-writing tools, `propose` and `promote` refuse with `invalid_arguments`) | always `agent:<consumer>` |
| HTTP | `rootmark serve --vault <v> --http 127.0.0.1:<port>` (`:0` a free port; the real port on stderr: `rootmark serve: http listening on 127.0.0.1:<port>`) | `Authorization: Bearer <.rootmark/server.token>` (required), `X-Consumer: <label>` (required, not empty) | always `human:<policy.toml [identity] human_id>` |

- `X-Consumer` is only a trace label (`traces.jsonl` `consumer`) and the provenance `source` of `propose`. It **cannot change** the actor kind.
- Over HTTP the **write endpoints** (`propose`, `promote`, `checkpoint`; since P2-0 §2.6's `attest_session`, `attest`; since P2-P §2.7's `demote`; since P2-R §2.10's `prune`) need `[identity] human_id`. Without it they return 403 `denied`. Reads and trace-writing reads (`search`, `read_block`) work without `human_id`.
- HTTP is on `127.0.0.1` only. Endpoints: `POST /v1/<tool>` (body = the tool's arguments, a JSON object; an empty body is `{}`), `GET /v1/status`, and the human channel's own endpoints `POST /v1/attest_session`, `POST /v1/attest` (§2.6; not on MCP). The body limit is `[server] max_propose_bytes + 1 MiB` (above it 413 `too_large`).
- **One process:** MCP and HTTP for the same vault must be opened together in a single `rootmark serve` process: `rootmark serve --vault <v> --mcp stdio --http 127.0.0.1:<port>`. The ordering guarantee of §5 holds only within one process. A second `rootmark serve` or a CLI write on the same vault is neither ordered nor locked (`docs/SECURITY.md`).

### 2.1 `propose` and the edit policy (K-D1.1)
- The agent's text is written to the file without adding any identifier, mark or metadata. Line endings follow the document's (CRLF in a CRLF document), a single line ending stays at the end, and `append` puts one blank line before it. The blocks are taken in with `author_kind: Agent`, `source` = the consumer, in the `proposal` layer. Until promoted they are not in the default search.
- `create` does not overwrite an existing file (`exists`). `append` adds after one blank line at the end of the existing document. `replace_section` replaces the body of the **single** ATX heading whose text (with the leading `#`s and closing `#`s and surrounding whitespace removed) is exactly `heading`, up to the next ATX heading of the same or a higher level (if there is none or more than one: `heading_not_found`). Setext headings (underlined with `===`/`---`) are not section boundaries.
- The default policy is `[edit] policy = "append_only"`. Whatever the channel, the following writes are refused with `denied` (403). The agent's text is written nowhere: neither the file, nor `proposals.jsonl`, nor the request's own events are written (for the exception see the external edit item at the end):
  - a write that changes, deletes, moves, splits or merges a canonical (or derived) block, or lowers its layer;
  - a write that changes a search unit (chunk) made only of canonical blocks;
  - a write that changes the front matter of an existing document;
  - a `replace_section` of a section containing a block that is not a proposal.
- **Client rule:** text appended to the end of a section a human wrote joins that section's chunk and is refused. Text to append must start with its own heading (`## Öneri: …`; §4.1, the agent guideline). Such an `append` without a heading returns `policy_violation` (422) with a `hint` (K-E0.4); a write that starts with a heading but still touches canonical content is `denied`. A section made only of proposal blocks (the agent's own proposal) can be corrected with `replace_section`.
- `[edit] policy = "unrestricted"` allows every write only if written explicitly. Even then delete and change events carry their actor.
- If there is an edit made outside the server that has not been taken in yet, it is taken in as a human write before the policy decision (`synced_external_events`). It stays in `events.jsonl` as the human's write even when the request is refused. These events are the human's, not the agent's.
- **Declarative promotion rules (P2-P/P1, K-Q.1 (2)).** The `[promotion]` table of `policy.toml` can carry an optional list of rules:
  ```toml
  [promotion]
  policy = "human_only"          # elle terfi için aynen
  version = "2026-10-25"         # kurallar varsa zorunlu, boş olmayan dize
  [[promotion.rules]]
  id = "official"                # [a-z0-9_-]{1,64}, tekil
  actor = "agent:collector"      # ajanın adı, tam eşleşme; yalnız agent:<id> (MCP istemcisinin <ad>/<sürüm> kimliği adıyla eşleşir)
  source = "collector"           # isteğe bağlı; propose'un köken source'u, tam eşleşme
  path_prefix = "sources/official/"  # vault-göreli; search.path_prefix'in kuralı (sondaki '/' atılır; '..', mutlak yol, boş önek reddedilir) ve NFC olmayan (NFD) yazım reddedilir
  to = "canonical"               # tek değer
  ```
  (The comments of the block, in Turkish, say: `policy` — unchanged for manual promotion; `version` — required when there are rules, a non-empty string; `id` — unique; `actor` — the agent's name, exact match, only `agent:<id>` (matches the name of an MCP client's `<name>/<version>` identity); `source` — optional, the provenance source of `propose`, exact match; `path_prefix` — vault-relative, the rule of `search.path_prefix` (a trailing `/` is removed; `..`, an absolute path, an empty prefix are refused) and a non-NFC (NFD) spelling is refused; `to` — the only value.)
  The agent's **name** is its identity, not its version: over MCP the actor and source are `<clientInfo.name>/<clientInfo.version>` (§1), on the CLI `--source`; `agent:collector` covers both `agent:collector` and `agent:collector/<version>` (the version not empty, without `/`), and nothing else (`collector2/…`, `collector/x/1`, a difference in case); a rule written with a version (`agent:collector/1.0`) covers only itself; `source` by the same rule (P2-P/P4, K-P2P.5). With `[promotion] policy = "deny"` rules are not loaded (a promotion by a rule could not be undone). The rule matcher runs **only on `propose`** (MCP, HTTP, `rootmark propose`) and after the call's `SnapshotCommitted`: every lineage the call wrote (whose version is new in this call) that is a live, unpruned `proposal` gets, in lineage id order, a single `Promoted` event from the **first** rule (in recipe order) that covers the call: `meta.actor = {kind: "policy", id: "<rule>"}`, `meta.reason = "rule:<rule>"`, `meta.policy = "rules"`, `meta.policy_version` = `[promotion] version`, `meta.from = "proposal"`, `meta.to = "canonical"`. The answer's `events` count includes these events and the answer carries them in the `promoted` field (an array of events); if no rule promoted, there is no `promoted` field (the answer and `events_hash` of a recipe without rules do not change). External changes taken in by the watcher (attested or not), a late attestation and a manual `promote` do not run the rule matcher: `unverified` content and unattested file writes are promoted by no rule. A human's (HTTP) `propose` does not match (a rule is only for `agent:<id>`). A write the edit policy refuses (`denied`, `policy_violation`) writes nothing and so is not promoted either. Undo: the human, with `demote` (§2.4).
  Load errors (naming the field): `actor` not `agent:<id>` (`human:…`, `policy:…`, `unattested_fs`), `to` not `canonical`, the form or a collision of `id`, `version` missing or empty when there are rules, an invalid `path_prefix`, an unknown field. With a faulty recipe `rootmark serve` does not start and every tool returns `policy_violation`; `rootmark policy lint <vault>` loads the recipe as `serve` loads it, lists the rules (normalised), and exits 1 on an error. The `status.policy` of a recipe with rules carries `promotion_rules {version, rules}` (no such field without rules).

### 2.2 `search` and `include_proposal` (spec §9, K-C1.3, K-D1.8)
- The default answer holds only `canonical` results; `derived` is never returned.
- With `include_proposal: true`:
  - the `canonical` results are **byte-equal** to those returned with the flag off (the same chunks, order, score);
  - then the `proposal` results follow: in a separate pass, ranked with canonical statistics only, labelled `layer: "proposal"`, score ×0.5.
  - `unverified` (spec 2.0.0) results come in the same pass as the `proposal`s, labelled `layer: "unverified"`, score ×0.5; they are not in the default answer.
- **Answer length (normative):** at most `k` hits per layer (`proposal` and `unverified` together `k`), at most `2k` in total.
- Every `search` and `read_block` writes a full consumption trace (`trace_id` in the answer). An empty query returns `empty_query` and writes no trace.
- The same checkpoint + query + mode + `k` → the same ordered result (spec §10).
- **Path prefix filter (P2-L/L3, GOAL P2-L 4):** `path_prefix: ["notes", "proje/2026"]` ranks only documents whose path is a prefix itself or lies under it (`prefix/…`); `notes` does not match `notes2/` or `notesx.md`. Prefixes must be vault-relative: they are turned into Unicode NFC (P2-B/B0, K-P2B.1: a prefix arriving in NFD or another non-NFC spelling is **folded**, not refused — a search is a read, `c` + U+0327 addresses the same prefix as `ç`; by contrast a promotion rule's `path_prefix` (§2.1) is an authority and an NFD spelling is refused at load), a trailing `/` is removed, they are sorted and deduplicated; an empty array, an empty prefix, more than 64 prefixes, a prefix longer than 1024 bytes, an absolute path (`/…`, `\\…`, `C:`), `\`, an empty, `.` or `..` component and a control character return `invalid_arguments` (400) and write nothing (no trace either) — a prefix cannot address outside the vault. The filter is applied before ranking: the candidate set is filtered, the statistics (BM25 `N`, `n`, average length) are those of all `canonical` chunks of the checkpoint; so in `lexical` and `flat` the filtered ranking is the unfiltered one's order among those documents with the same scores (`hybrid` merges the filtered top 50 of both sides). `include_proposal` keeps its meaning: both passes are filtered, and the canonical part is byte-equal to the same filtered search's result without the flag. `query_hash` stays `H(query)` in an unfiltered search; in a filtered search it is `H(query + "\n" + {"path_prefix": [...]})` (normalised prefixes, JSON). The answer carries `filter {path_prefix}`; the trace returns with the `filter` field in a `trace` call (`.rootmark/trace_filters.jsonl`, by `trace_id`; the lines of `traces.jsonl` keep spec §8's fields). The answer and trace of an unfiltered search do not change.
- **Date filter (version 2; P2-B/B3, K-Q.1 (3b)).** `date_from`, `date_to` (each optional, inclusive, an exact `YYYY-MM-DD` calendar day; `date_from` cannot be after `date_to`) rank only documents whose date is in the range. A document's date is derived only from one of two sources in the vault's recipe — **never** from the file time (mtime):
  - `[index] date_from_path = "{yyyy}/{mm}/{dd}"`: the first match in the document's path starting at the beginning of a component (`{yyyy}` four digits, `{mm}` and `{dd}` two; after the match the end of the path, `/`, `.` or a non-digit character; a valid calendar day);
  - `[index] date_field = "date"`: the front matter's top-level `date: <value>` line (unquoted or quoted; the value's first ten characters `YYYY-MM-DD`, then only a time beginning with `T` or a space).
  Both at once, a pattern that does not carry `{yyyy}`/`{mm}`/`{dd}` once each, an unknown `{…}`, an absolute pattern or one containing `\`, an empty key are load errors of the recipe (naming the field; `rootmark serve` does not start). In a vault without a date source a date filter, a malformed day and a reversed range return `invalid_arguments` and write nothing. The date is computed from the path of the documents at the search's checkpoint and from that version's front matter; it enters no identifier, event or md. A document whose date cannot be derived stays out when there is a filter, and the answer gives the number of such documents in `undated_excluded`. The date filter combines with `path_prefix` (documents that satisfy both); `filter` and the trace (`trace.filter`) carry the fields given (`date_from`, `date_to`; `path_prefix` only if given) and `query_hash` covers the filter by §2.2's rule. The answer, `query_hash` and trace of an unfiltered search and of a search with `path_prefix` only do not change.

### 2.3 Checkpoint flow (spec §8, K-D1.6)
- A state has one checkpoint. Its id derives from the content and the event offset. An unnamed `checkpoint {}` returns the state's existing checkpoint. If that checkpoint is named → `exists`.
- A `search`/`read_block` without `at` creates the current state's **unnamed** checkpoint (if there is none).
- `checkpoint {name}` works like this:
  - (a) if the state has no checkpoint, creates it named;
  - (b) if the state has an unnamed checkpoint, names it (the same id);
  - (c) if the same name is given again, returns the same checkpoint.
- Another checkpoint's name, or another name for a named state → `exists`. A name cannot be empty; it cannot have whitespace at its start or end or a control character; it cannot have the form of 32 hex (`invalid_arguments`). Inner spaces are allowed.
- Recommended flow: first `search`/`read_block`, then `checkpoint {name}` (the order does not matter). To go back to yesterday's state use `search {at: <name>}`.

### 2.4 `promote` (spec §7, K12/K16, K-D1.3)
- The kernel does not decide; `policy.toml [promotion]` decides (default `human_only`).
- An unknown or non-live lineage → `not_found` (before the policy, on both channels).
- The policy's refusal is an **answer, not an error**, on every channel: `decision: "denied"` (HTTP 200), no event is written. A request from MCP (actor `agent`) always returns this under `human_only`. A request from HTTP returns this under `[promotion] deny`.
- A request from HTTP (`human_id` set) under `human_only` → `decision: "promoted"` and a `Promoted` event (`meta.actor {kind: human, id}`; P2-P/P3: `meta.source` = the request's `X-Consumer`, §4.2).
- If a request the policy allows is for a lineage that is not `proposal` or `unverified`, or is pruned → `invalid_arguments` (HTTP 400). The promotion of an `unverified` lineage carries `meta.from = "unverified"` in the `Promoted` event (spec 2.0.0 §7).
- A chunk takes the lowest layer of its blocks. To make a document visible in search, all lineages of the chunk are promoted.
- **Promotion by a rule (P2-P/P1).** `[promotion] policy` (`human_only`/`deny`) governs only manual promotion (this tool); the promotion of declarative rules happens on `propose` (§2.1). The `Promoted` event of a lineage promoted by a rule carries the rule (`meta.actor {kind: policy, id: <rule>}`, `meta.reason "rule:<rule>"`, `meta.policy "rules"`, `meta.policy_version`); `history` shows it (no new field). The kernel's reading rule: the `reason` of a `Promoted` with a `policy` actor has the form `rule:<rule>`, `<rule>` is the event's `meta.actor.id`, `meta.from` is `proposal` (P2-B/B0; a rule promotes only an agent's proposal) and its `policy_version` is not empty; otherwise the vault is refused when opened (the reference implementation's rule; the spec text does not change).

### 2.5 The inner fields of answers a client relies on (P1-E/E1)
The inner structure of the main fields of the §2 table. This is P1-D.1's behaviour (nothing new); a client relies only on what is here and checks it in every answer (a missing field or one of the wrong type → `bad_response` in the client, no silent acceptance). Fields not written here can come; the client does not rely on them.
- Block summary (`blame.blocks[]`, `propose.blocks[]`): `lineage_id`, `version_id` (string), `layer` (`canonical`\|`proposal`\|`unverified`\|`derived`; `unverified` 2.0.0), `layer_source` (string), `author_kind` (string: `Human`, `Agent`, `Transcript`, `Synthetic`), `source` (string, can be empty for a human write), `seq_created`, `seq_last` (integer), `inactive` (boolean). In document order (snapshot order).
- Event (`history.events[]`, `promote.event`): `seq` (integer), `kind` (string), `doc_path` (string), `lineage_ids` (array of strings), `meta` (object; §4.2's `actor {kind, id}`, `source`; in `Promoted` `reason`, `from`, `to`).
- Read block (`read_block.block.block`): `version_id`, `lineage_id`, `block_type`, `text` (string), `heading_path` (array of strings), `layer`, `provenance {author_kind, source}`.
- Hit (`search.hits[]`): `doc_path`, `chunk_id` (string), `lineage_ids` (array of strings), `layer`, `score` (number); v2: `loc` (an array in the same order as `lineage_ids`, each item a position or `null`), `loc_stale` (boolean).
- **Block position (version 2; P2-B/B1, K-P2B.1).** `blame.blocks[]`, `read_block.block` and (if `search` was called with `loc: true`) `search.hits[].loc[]` carry for each block an optional `loc {line_start, line_end, byte_start, byte_end, content_hash}`; the answer (`blame`), the read block (`read_block.block`) and the hit carry an optional `loc_stale` (boolean).
  - `line_start`, `line_end` (integer): 1-based, inclusive, lines counted over the whole document including the front matter. `byte_start`, `byte_end` (integer): UTF-8 byte offsets in the document's bytes, a half-open range; the block's raw text, the trailing line ending not included. `line_start` is the line of `byte_start`, `line_end` that of `byte_end − 1`. `content_hash` (string): the hash of the document bytes the positions belong to (the same definition as §2.6's `content_hash`: the first 32 lowercase hex of BLAKE3).
  - A position belongs to the bytes of the **version** the answer describes (the current head or the `at` checkpoint). If the file on disk parses into this version's blocks (the same version ids, the same order) the positions are the file's own and `loc_stale: false`; otherwise (the file changed without being taken in, was deleted, or the answer is of an old checkpoint) `loc_stale: true` and the positions are those recorded when that version was taken in (`.rootmark/loc/`, derived). The server does not apply an old offset to a new file. In a version whose positions were not recorded (a document taken in before P2-B whose file no longer holds that version) the blocks carry no `loc`; there is no silent guess.
  - **Experimental (P2-B decision rule, K-P2B-T1).** In the pre-registered alignment measurement (`reports/rounds/P2-B/b2/`) 0.00551 of the blocks failed the slice criterion (threshold 0.005): on real notes per class `code_fence` 0.00521, `nested_list` 0.00393, `footnote` 0.00275, `html` 0.00249, `crlf` 0.00241, `callout` 0.00079, `table` 0.00043, `frontmatter` 0.00022, `embed` 0, Turkish 0; on seeded edge cases `bom` 0.00435, `html` 0.00128, the other nine classes 0; no coverage error at all. The known cause: in an indented code block `byte_start` is after the first line's indentation (the lines are right). Therefore a client uses a position together with a **slice check**: the `version_id` computed from `bytes[byte_start..byte_end]`, normalised by spec §2.1, with a block type (`H(type + "\n" + normalized_text)`) must equal the block's `version_id`; otherwise that block counts as having no position. **P2-R/R0 (K-P2B-T1 (a), K-P2R.2):** an indented code block's `byte_start` is now the start of the first line (indentation included; the raw text, the identifiers and the events unchanged), and the slice parsed on its own is the block itself; the re-measurement with the same corpus, seed and frozen measurer (`reports/rounds/P2-R/r0/`) gives **0.00000** on real notes (28 111 blocks), Turkish 0, on edge cases `bom` 0, `html` 0.00128 (two cases caused by context, the criterion's limit), the other nine classes 0. For the `Code` type the slice check also tries the slice with the first line's first four columns of indentation skipped (spaces; a tab to the next multiple of four) (the block's raw text starts after the indentation). The position is still experimental and slice-checked (K-P2B-T1 (c)).
  - Client rule: a client uses a position only if the hash of the bytes it holds equals `content_hash`; with `loc_stale: true` it does not guess lines (the Obsidian panel says "stale"). Without `loc` (a version 1 server) it can fall back to the old order mapping.
  - A position is derived information: it enters no event, identifier, `events_hash` or trace; nothing is written into md. `propose.blocks[]` carries no position. In `search` the position is optional (`loc: true`): the answer of a search without `loc` is byte-equal to version 1's (every write of a document changes its `content_hash`; version 1 clients and recorders that check the byte equality of canonical results are not affected). `loc` does not change the trace, `query_hash` or the ranking.
  - CLI: `rootmark blame --loc` and `rootmark replay --loc` write the same positions (the output without the flag is unchanged).
- Trace (`trace.traces[]`, `read_block.trace`): `trace_id`, `checkpoint_id`, `consumer`, `query_hash` (string), `at_seq` (integer), `returned[{doc_path, lineage_id, version_id}]`.
- Checkpoint (`checkpoint`, `checkpoints[]`, `status.last_checkpoint`): `checkpoint_id` (string), `name` (string or `null`), `event_seq` (integer), `docs` (object: `doc_path` → snapshot id). `status.last_checkpoint` is `null` if there is no checkpoint.
- `status.migrations` (P2-A, K-P2A.2; the version matrix): `artifacts` (object; keys `store`, `events`, `attestations`, `index`, `checkpoints`, `policy` (P2-P/P0, K-P2L-T1: the recipe's `[attestation]` table — `format` `recipe/attestation`, `recipe/implicit` in a recipe without the table, `null` if there is no recipe; `state` always `ok`; an unreadable recipe (not TOML) is not a row but an error of the matrix: `status.migrations` becomes `{"error"}`, P2-B/B0; a recipe without the table does not become `migration_required`); each of them `{format, expected, state}` — `format` the format on disk (a string, or `null`: absent), `expected` this `rootmark`'s format (string), `state` `ok`\|`migration_required`\|`unknown`; an optional `note` string), `required` (array of strings: migrations that must be applied and change bytes — `rename_store`, `index_rebuild`), `recommended` (array of strings, P2-P/P0: migrations that change bytes but no vault requires — `policy_attestation_1`: adds `[attestation] unattested = "canonical"` to a recipe without the table, the rest of the file kept byte for byte, with a rollback record; does not affect `hint`), `validations` (array of strings: validation migrations that have no record yet — `log_readers`, `checkpoints`; they change no bytes and are not required), `applied` (array of strings: the record ids under `.rootmark/migrations/`, oldest first), `hint` (string or `null`: `rootmark migrate <vault>` if `required` is not empty). `status` returns 200 even when a migration is needed. - `status.attestation` (P2-0): `unattested` (string: `unverified`\|`canonical`), `implicit` (boolean, P2-P/P0: the recipe has no `[attestation]` table — `unattested` is not a choice but the kernel's reading without the table; `rootmark serve` writes a warning line at start, `rootmark migrate` adds the table), `window_s` (number), `stage` (integer), `pending` (integer).
- `status`: `spec_version`, `mdk_version` (string), `level_claimed` (integer), `embedder` (string or `null`: the `embedder_id` of the index manifest on disk; `null` if there is no manifest or it cannot be read), `index` (object, K-E1.2), `policy.promotion`, `policy.edit` (string), `server_policy.identity.human_id` (string or `null`).
- `status.index` (K-E1.2; replaces the `"absent"`/`"present"` string of P1-E/E0): `state` (string: `ok` — the manifest is in this implementation's format and lexical record; `stale` — the manifest is readable but in another format or lexical record, an older `rootmark`'s index; `missing` — no index directory or manifest; `damaged` — the manifest cannot be read or decoded), `format` (string or `null`: the `format` of the manifest on disk), `expected_format` (string: this `rootmark`'s format), `auto_rebuild` (boolean: the vault policy's `[index] auto_rebuild`). `status` reads only the manifest: an index whose files disagree with the manifest looks `ok` and returns `internal` on calls that need the index (§3). ### 2.6 Attestation endpoints — HTTP only (P2-0, spec 2.0.0 §7.1; K-P2-0.5)
A human-channel client attests the bytes it saved after every save. These endpoints are not tools: they are not in MCP `tools/list`, and a call from MCP is an unknown tool (the §3 exception). Both need the token and `[identity] human_id` (otherwise 403 `denied`) and pass through the queue like writing calls.

| Endpoint | Body | Successful answer |
|---|---|---|
| `attest_session` | `{}` | `session_id` (string), `key` (64 hex: an HMAC-SHA256 key), `ttl_s` (integer), `stage` (integer: 1 = a session key obtained with the token; 2 = the keychain, Z6) |
| `attest` | `doc_path`, `content_hash` (the first 32 lowercase hex of the BLAKE3 of the file's bytes), `saved_at_seq` (optional, integer), `session_id`, `mac`, `late` (optional boolean, default `true`; `false`: the attestation is only written to the log — it raises no change already taken in and matches no later observation), `renamed_from` (optional: the client's rename; the server checks that the bytes of the file at `doc_path` equal `content_hash` and its blocks exactly the head snapshot of `renamed_from` — or that only the note's own links were rewritten by the `link_update_of` rule — otherwise 403 `denied`; since P2-0.2 the head may also carry non-`canonical` blocks: a rename **carries** every block's layer **as it is** — `canonical` `canonical`, `unverified` `unverified`, `proposal` `proposal`; no block is raised or lowered — the one exception is a `proposal` of `human` origin (a proposal the human edited): §7 cannot record it as a `proposal` in the new lineage, it is carried as `unverified` (lower, never higher); a late rename attestation also raises only blocks that were `canonical`/`proposal` on the old path, up to that layer; spec §7.1 "Rename"), `link_update_of` (optional, P2-0.1: the **new** path of the renamed note; the links the client updated in another note (or in the note itself) during a rename; the server checks that the bytes of the file at `doc_path` equal `content_hash` and differ, block by block, from the document's head snapshot — if the log does not know the document yet, from the head of the path it came from through an accepted rename — only in link targets naming `link_update_of` (P2-0.2: and in the label of a Markdown link whose label is the old target's name — the file name without `.md`, or the target as written — turning into the same form of the new target), that every block that changed in another note is live and `canonical` (in the renamed note itself blocks may be in any layer and their layers are carried as with `renamed_from`; if the log does not know the new path yet, the check is made against the head of `link_update_from` when there is no accepted rename attestation), that at least one target changed and — if the old path is known from an accepted rename attestation — that every old target names that path; if the watcher took in the same bytes before the attestation, the check is made against the head before that ingest — if in that ingest the path was new to the log and the document is the renamed note itself, not against the empty head before the ingest but against the head of the old path (from the accepted rename attestation or from a `link_update_from` whose file is not on disk; P2-A/A0, spec §7.1); otherwise 403 `denied`; if `link_update_of` is not a note in the vault, 403 `denied`; together with `renamed_from`, `invalid_arguments`), `link_update_from` (optional, only with `link_update_of`: the renamed note's old path; if the server does not know the old path from an accepted rename attestation, it checks that every old target that changed names it), `content` (optional, P2-0.1: the saved bytes, UTF-8 text; `invalid_arguments` if its BLAKE3 is not `content_hash`; the server keeps it in memory only for the window and writes it nowhere; for the partial match, below) | `attestation_id, doc_path, content_hash, at_seq` (integer), `recorded` (boolean: `false` → the same attestation is already recorded), `raised` (array of strings: the lineages a late attestation raised) |

- `mac` = `HMAC-SHA256(key, "rootmark-attest/1\n" + doc_path + "\n" + content_hash + "\n" + saved_at_seq)` (decimal; empty if absent), 64 lowercase hex. An unknown or expired session, a wrong `mac` → 403 `denied` (the client opens a new session once and retries). A malformed `doc_path` → `path_outside_vault`/`invalid_arguments`; a `content_hash` that is not 32 lowercase hex → `invalid_arguments`.
- Matching (spec §7.1): an external change the watcher sees is taken in as `canonical` (human) if it matches an attestation recorded within `[attestation] window_s` (default 2.0) seconds for the same `(doc_path, content_hash)`; if it does not match, `unverified`, actor `unattested_fs`. An attestation arriving later within the window raises that ingest's lineages to the layer an attested ingest would have given (`canonical`; for a touched `proposal`, `proposal`): `raised`, event `LayerChanged` `meta.cause = "late_attestation"`.
- `[attestation] unattested = "canonical"` (policy) returns to the old behaviour: every external change is the human's, `canonical`. The recipe `rootmark serve` writes into a vault without a `policy.toml` carries this line explicitly (P2-A/A0, K-P2-02.5): the actual default of new installations is `canonical`; `unattested = "unverified"` is optional and is the default of the kernel (of spec §7.1) when there is no table at all. `status.attestation.unattested` says which applies; `window_s` the window, `stage` the key stage, `pending` (unattested ingests waiting in the window), `link_updates` (P2-0.1: link update attestations accepted since the server started), `unmatched` (P2-0.1: lines of the attestation log marked `matched: false` — at the moment it was recorded the file did not hold the attested bytes, nor, if it came with `content`, their blocks, and there was no pending change of those bytes in the window; the attestation is not refused, only marked).
- CLI: `rootmark attest <vault> <doc>… [--renamed-from <old>]` / `--all` sends the same two endpoints to the running server (right after the save; the window applies). An attestation raises every unattested change within the window that contains the same bytes: users attest only documents they saved themselves. `--all` attests every document with `late: false`: only a record goes into the log, no layer changes (a bulk attestation reads the files as they are; it cannot launder an agent write not yet observed). To count a document as attested, attest it by name right after the save.
- **Diagnostic log (P2-A/A0):** `rootmark serve --attest-log <file>` (the file must be outside the vault; otherwise the server does not start) writes every `attest` call (`accepted` or `refused` + code + reason) and every observation of an external change (for `attested`/`partial`, the `seq` distance of the attestation; for `unverified`, the same document's unmatched accepted attestations and why) as JSON lines. It is not part of the contract: a client does not rely on it, the server does not read it.
- A late attestation raises only lineages still standing in the version the unattested change gave; if someone else changed that paragraph afterwards it does not raise it (spec §7.1).
- **Partial match** (P2-0.1, spec §7.1 "Partial match"): if the bytes the watcher sees match no attestation exactly but contain the blocks (as a multiset of versions) of an attestation with `content` within the window, the attested bytes are first taken in as an attested ingest (`canonical`), a line `{…, partial: true}` goes into the log, then the observed bytes are taken in as an unattested ingest (`unverified`): a human's save and an agent's write that fall into the same observation are separated. If the attestation comes after the change (late), the file does not hold the attested bytes at that moment, the window has a single unattested ingest containing those blocks, and the saved bytes hold all the blocks that ingest left as they were, then only the lineages matching the attested blocks are raised (`raised`) and the attestation line carries `partial: true`. The plugin and the CLI send `content` (except CLI `--all`).
- An attestation matches at most one change (P2-0.1, spec §7.1 "One match per attestation"): once matched it is consumed; an unattested ingest of the document voids the attestations recorded before it. A client that saves the same bytes again attests again.

### 2.7 `demote` — HTTP only (P2-P; K-E2-T (a), K-P2P.3)
The endpoint by which a human undoes a promotion (including a promotion by a rule, §2.1). It is not a tool: it is not in MCP `tools/list`, a call from MCP is an unknown tool (`not_found`); it needs the token and `[identity] human_id` (otherwise 403 `denied`) and passes through the queue like writing calls.

| Endpoint | Body | Answer |
|---|---|---|
| `POST /v1/demote` | `{lineage_id, reason, to?}` (`to`: `proposal`\|`unverified`\|`derived`; if absent, one layer down: `canonical` → `proposal`, `proposal`/`unverified` → `derived`) | like `promote`: `decision: "demoted"` + `event` (`Demoted`, `meta.actor {kind: human, id}`, `reason`, `from`, `to`, `policy`, `policy_version`) and the new `layer`; the policy's refusal (`deny`) `decision: "denied"`, no event; an unknown or non-live lineage `not_found`; a `to` that does not lower, or a pruned lineage, `invalid_arguments`. |

The decision is the `[promotion] policy` hook's (`human_only`: the human; `deny`: nobody). `Demoted` lowers the lineage to `proposal`: invisible in the default search, returned labelled with `include_proposal`; `history` shows both events.

### 2.8 `events` — the event stream (version 2; P2-B/B3, K-Q.1 (4))
A read-only, pull event stream (HTTP `POST /v1/events`, MCP `events`): there is no push, subscription or websocket; the client asks for the next page with `next_seq`.
- Returns the events of `events.jsonl` from `since_seq` (inclusive) in seq order; each event object is the **bytes** of its line in the log (byte for byte in the HTTP body and in MCP `content[0].text`; MCP `structuredContent` is the same objects). `head_seq` is the log's length (the seq of the next event).
- `limit` (default 100) is the upper bound of the returned events; outside 1–1000 `invalid_arguments` (not clamped). `next_seq` is the next page's `since_seq`: if the page is full, the seq after the last returned event, otherwise `head_seq`. `since_seq > head_seq` is `invalid_arguments`; `since_seq = head_seq` gives an empty page and `next_seq = head_seq`.
- `kinds` (event kind names; an unknown name `invalid_arguments`) and `path_prefix` (§2.2's rule: folded to NFC, a prefix addressing outside the vault refused; vault-wide checkpoint events — empty `doc_path` — match no prefix) only filter, they do not change the order; the answer carries the normalised `filter`.
- `events` writes nothing: events, traces (`traces.jsonl` included) and other files stay as they are; `events_hash` does not change. **It writes no trace.** Like a read it waits for the writers (§5); it needs no consumer identity.

### 2.10 `prune` — retention and pruning, HTTP only (an addendum to version 2; P2-R, K-P2R.1, K-P2R.2)
The explicit pruning call of a human (or an operator). It bounds `.rootmark`, but rootmark **does not delete** a governance record: a proposal prune is an event, a trace and checkpoint prune is a **move** into the archive, and the only deletion is of derived position records. It is not a tool: it is not in MCP `tools/list`, a call from MCP is an unknown tool (`not_found`) — an agent cannot prune. It needs the token and `[identity] human_id` (otherwise 403 `denied`) and passes through the queue like writing calls (§5). `rootmark serve` does not prune by itself (not at shutdown, in the watcher or on a query); the CLI `rootmark prune <vault> [--dry-run] [--now-ms <ms>]` does the same job (not while the server runs: §1, "one process").

| Endpoint | Body | Answer |
|---|---|---|
| `POST /v1/prune` | `{dry_run?, now_ms?}` (`dry_run` default `false`; `now_ms` only the time of the raw journal's prune, the clock if absent) | `{dry_run, events_hash_before, events_hash, rules {version, rules[], pruned[{doc_path, lineage_id, layer, rule, last_seq, idle_checkpoints}], events[]}, retention {keep_checkpoints, bound, traces {base_before, base, lines, archive, filter_lines}, checkpoints[], loc {removed[{doc_path, snapshot_id}], kept}, note?}, journal {now_ms, records_removed, records_kept, blobs_removed}}` |

- **Recipe** (`policy.toml`; an invalid recipe is `policy_violation`, nothing is clamped): `[prune] version` and `[[prune.rules]] {id, layer, idle_checkpoints, path_prefix?}` — `layer` `proposal` or `unverified` (never `canonical`), `idle_checkpoints` ≥ 1, `path_prefix` a list of vault-relative prefixes (NFC; NFD refused, §2.2's rule); `[retention] keep_checkpoints` ≥ 1.
- **Proposal decay** (spec §7, K19-T): the first covering rule decides (recipe order, its layer the lineage's, its prefixes cover the document); if at least `idle_checkpoints` checkpoints were created after the lineage's last event, a `Demoted` event: `meta.prune: true`, the layer unchanged (`from = to`), `meta.actor {kind: "policy", id: <rule>}`, `meta.reason "rule:<rule>"`, `meta.policy "prune_rules"`, `meta.policy_version`; over HTTP `meta.source` is the request's `X-Consumer` (§4.2). With a recipe without rules no event is written, `events_hash` unchanged. A pruned lineage is `inactive: true`: from that checkpoint on it is not in search (`include_proposal` included), `read_block` reads it with `inactive: true`, and at a checkpoint before the prune `at` returns the earlier answer unchanged; `history` shows the event.
- **Retention bound:** the oldest of the last `keep_checkpoints` checkpoints in creation order. In a recipe without the table there is no bound: traces and checkpoints are not archived and the answer says so with `retention.note`.
- **Trace archive:** from the start of `traces.jsonl`, the longest run of lines that read a checkpoint before the bound's `event_seq` is moved, byte for byte and in the same order, to `.rootmark/traces/archive/<first at_seq>-<last at_seq>.jsonl` (the `trace_filters.jsonl` lines of filtered searches beside it as `….filters.jsonl`). `at_seq` is **absolute**: the `at_seq` of the first live trace is in `.rootmark/traces/base`, the remaining traces' `at_seq` and `trace_id` do not change, new traces continue the count (spec §8, informative note). `trace` carries `archived_before: <base>` if `since_seq < base` (not silent); `rootmark trace list <vault> --archived` reads the archive. The live file joined after the archive is the old file.
- **Checkpoint archive:** the file of a checkpoint behind the bound that is unnamed and read by no live trace is moved to `.rootmark/checkpoints/archive/<id>.json`; its id does not change, it appears in the `checkpoints` list with `archived: true`. A named checkpoint is never archived. A query at an archived checkpoint with `at` (`search`, `read_block`, `blame`) is refused with the code **`archived`** and names the archive file; no trace is written.
- **Position records** (§2.5): the records of the versions named by the documents' heads and by live checkpoints stay, the rest are deleted (a version without a record has no `loc`, no silent wrong offset).
- **Known limit (0.3.0; Block 2 verification F1, K-P2Q.2):** a live `canonical` block that shares a search unit (chunk) with a block a prune rule made `inactive` is not returned by `search` after that prune (the index view leaves the chunk out as a whole). Nothing is deleted: the block is read with `blame` and `read_block` and at the checkpoints before the prune. Before pruning, `dry_run: true` shows the plan. Its fix is pre-registered work of P2-C.
- **Raw journal:** `journal prune` unchanged (spec §11; older than `[journal] retention_hours` before `now_ms`).
- **Determinism:** the prune decision derives only from the log (`seq`), the checkpoint order and the recipe; it does not look at the clock (`now_ms` only for the raw journal). The same vault + the same recipe + the same call → the same live files, the same archive and a byte-for-byte identical answer. `dry_run: true` returns the same plan and changes no file.
- **`status.retention`** (optional; only in a recipe that carries `[retention]` or `[[prune.rules]]`, or in a vault with an archive): `{keep_checkpoints, traces_base_at_seq, archived_traces, archived_checkpoints, rules[]}` — `traces_base_at_seq` the `at_seq` of the first live trace (= the number of archived traces), `archived_checkpoints` the number of archived checkpoints, `rules` the rule ids.
- `events.jsonl`, `objects/`, `snapshots/`, `attestations.jsonl` are never pruned, moved or rewritten; rootmark does not delete the archive. A corrupt `traces/base`, a missing or extra archive file, a checkpoint file deleted by hand make the vault fail to open, and the error names the file.
- **A prune cut short** (P2-R reviewer finding 2): a prune first writes and syncs the archive file, then replaces `traces.jsonl` (and `trace_filters.jsonl`) by renaming a synced temporary file, and last `traces/base`. If it is cut in between, the vault does not open and the error names `traces/base` or the archive; rootmark does not repair it by itself. Repair (a human): if `traces.jsonl` still starts at the old `base`, move the last archive file (and, if present, the same range's `….filters.jsonl`) out of `.rootmark/traces/archive/` and run the prune again (it rewrites the same file byte for byte); if `traces.jsonl` already starts at the new `base`, write the last archive file's `<last> + 1` value and a line ending into `traces/base`. Checkpoint files are moved one by one; a move cut short keeps the vault open (each file is either live or archived), and running the prune again moves the rest.
- **No CLI prune while the server runs** (P2-R reviewer finding 3): the CLI changes `traces.jsonl` by renaming it; if the server appends a trace to the old file at the same moment, that trace line can be lost (§1, "one process": a CLI write does not enter the server's queue, there is no lock). If the server runs, use `POST /v1/prune` (it goes through the queue).
- `now_ms` (the HTTP body and the CLI's `--now-ms`) is only the time of the raw journal's prune and, like `rootmark journal prune --now-ms`, it is not bounded: giving a future time effectively shortens the journal's 24-hour lower bound for that call (an unversioned record and a document's last record are still not deleted, spec §11). This is a human-channel action (token + `human_id`).

## 3. Error codes (K-D1.5)
A failed tool call returns in these forms:
- **MCP:** `result.isError: true`, `content[0].text` = `"error: <mesaj>"` and `structuredContent = {"error": {"code": "<kod>", "message": "<mesaj>"}}`.
- **HTTP:** the status code from the table below, the body `{"error": {"code", "message"}}`.
- Some errors also carry `"hint"` (`{"error": {"code", "message", "hint"}}`): what the caller can do, a stable string. Examples: an `append` without a heading → `"hint": "start the appended text with a heading"` (K-E0.4); `migration_required` → ``"hint": "run `rootmark migrate <vault>` (it keeps a rollback record)"`` (P2-A). The client shows the hint to the user; without a `hint` there is no field.

A client decides by `code` only. `message` is for people and can change.

| Code | HTTP | Meaning |
|---|---|---|
| `invalid_arguments` | 400 | An argument that does not fit the schema or a rule (type, unknown field, `k` range, mode, a name not ending in `.md`, empty `reason`, the use of `heading`, no consumer identity). Over HTTP a missing/empty `X-Consumer`, a body that is not a JSON object and a wrong method (405) carry this code too. |
| `empty_query` | 400 | An empty or whitespace-only query. |
| `path_outside_vault` | 400 | A path that leaves the vault or its documents: `..`, absolute, a hidden component (`.rootmark/`), a symlink. |
| `denied` | 403 | A refusal by the policy or the channel: the `append_only` edit policy, an HTTP write without `human_id`, an unknown/expired session or a wrong `mac` in an attestation (§2.6). 401 (missing/wrong token) also carries the code `denied`. |
| `not_found` | 404 | An unknown lineage, document, checkpoint, tool or HTTP path. A document that does not exist, for `append`/`replace_section`. |
| `exists` | 409 | What would be created exists: an existing document with `create`; a path whose `doc_path` or a directory component differs from an existing document or directory only by case or Unicode form (`SUB/b.md` ↔ `sub/`; on every platform, K-GH.6: a vault stays portable between macOS and Linux); a checkpoint name already taken; another name, or an unnamed request, for a named state. |
| `too_large` | 413 | `content` exceeds `[server] max_propose_bytes`, or the HTTP body exceeds the limit. |
| `heading_not_found` | 422 | The `replace_section` heading is not in the document, or there are several. |
| `policy_violation` | 422 | The vault's `policy.toml` is invalid; or an agent's `append` to human blocks was refused under `append_only` because it did not start with its own heading (K-E0.4; carries a `hint`). |
| `archived` | 410 | The file of the checkpoint queried with `at` was archived by a retention prune (§2.10; P2-R): the query is refused and the message names the archive file (`.rootmark/checkpoints/archive/<id>.json`). Named checkpoints and those read by live traces are not archived. |
| `migration_required` | 503 | The vault's index is in an older format this `rootmark` can migrate (`status.migrations.artifacts.index.state = "migration_required"`; P2-A): `rootmark migrate <vault>` (with a rollback record; `--dry-run` says first what will change) or `rootmark index build`. Carries a `hint`. Only calls that need the index return it; `status` does not. |
| `index_stale` | 503 | The vault's index is missing, in a format this `rootmark` does not know, or its manifest cannot be read (K-E1.2; an older version's migratable index is `migration_required` since P2-A): it must be rebuilt (`rootmark index build`, or, for a missing/older format, restarting `rootmark serve` with `[index] auto_rebuild = true`; K-E0.3). A recoverable state, not `internal`. Only calls that need the index return it; `status` returns it in no index state. |
| `internal` | 500 | A server or vault error (e.g. an index file that disagrees with its manifest). An error to report, not a silent success. |

Exceptions:
- Over MCP an unknown tool is a JSON-RPC error (`-32602`). Over HTTP it is 404 `not_found`. The endpoints of §2.6 are unknown tools for MCP (`attest`, `attest_session` → `-32602`).
- At start `rootmark serve` builds the index if there is none; if it is in another format it rebuilds it with `[index] auto_rebuild = true` (the default). With `auto_rebuild = false` it leaves the index as it is, writes to stderr, and calls that need the index (`search`, `propose` in a vault that carries an index) return `index_stale`. It never rebuilds over an unreadable manifest (`damaged`) by itself, whatever the setting; calls that need the index still return `index_stale`. Read-only calls (`blame`, `history`, `checkpoints`, `trace`, …) work without an index too (K-E0.3); `status` returns 200 in every index state and reports the state in `index.state` (K-E1.2).
- **Shutdown (P2-0/Z0):** `rootmark serve` stops on SIGTERM/SIGINT or at the end of the MCP stream; it compacts the hot layer into the cold index and exits 0, or 1 if the compaction fails. If `index.state` is not `ok` (`stale`, `missing`, `damaged`) there is nothing to compact: the note `rootmark serve: compact (shutdown): skipped, index <state> …` is written to stderr and the exit is 0 (the timer's compaction is skipped with the same note). The index is still not built by itself.
- The policy's `promote` refusal is an answer, not an error, on every channel (§2.4).

## 4. Events, provenance and the agent guideline

### 4.1 The agent guideline (K-E0.4, K-D1.1)
- When an agent writes into a human document (one written by a human, containing `canonical` blocks) with `append`, it starts the text with **a new heading** (`## …`). The text then opens its own section and its own chunk, touches no canonical block or canonical search unit, and is accepted under `append_only`.
- An `append` without a heading that joins the chunk of a human section is refused: `policy_violation` + `hint: "start the appended text with a heading"`. Nothing is written.
- An agent corrects its own proposal (a section made only of proposal blocks) with `replace_section`. Changing or deleting a human section is `denied`; the way to do it is the human.
- The description of the MCP `propose` tool states this guideline (`tools/list`).
- **A vault with rules (P2-P).** If the vault's recipe carries a promotion rule (`status.policy.promotion_rules`), the content an agent writes, as the rule's agent, under the rule's prefix becomes `canonical` **without approval**: it enters the default search at once and counts as knowledge. The agent writes under this prefix only the content the rule intends (e.g. text taken unchanged from an official source); it writes comments, summaries and its own conclusions outside the prefix (where they stay `proposal` and wait for a human's approval). The answer's `promoted` field says which lineages were promoted; the human can undo it with `demote`. Scene: `docs/HEADLESS_CHANNEL.md` (development repository), "Sahne".

### 4.2 Events and provenance (spec §4.3, K-D1.2)
- The delete and change events in the output of `history` (`BlockDeleted`, `BlockUpdated`, `BlockMoved`, `BlockSplit`, `BlockMerged`) carry `meta.actor {kind, id}` and `meta.source` if they were written through the server. The actor comes from the channel: `agent:<client>`, `human:<human_id>`; for external edits taken in by the watcher, `human:<human_id>` or `human:unidentified` if attested (or if the policy is `canonical`), `{kind: "unattested_fs", id: "fs"}` and `meta.source = "unattested_fs"` if unattested (spec 2.0.0 §7.1; in blame `source` `unattested_fs`, `layer` `unverified`).
- Events written before 1.0.3 and `rootmark ingest`/`ingest-dir` (the low-level kernel path) carry no actor. A client shows this as "actor not recorded" and invents no actor.
- **The channel label of a transition (spec 2.0.3 §7; P2-P/P3, K-P2P.4).** `Promoted` and `Demoted` (`meta.actor` is the transition's actor: a human, an agent or a rule) carry an optional `meta.source`: the label of the channel the request came through. HTTP `promote` and `demote` (§2.4, §2.7) write it from the `X-Consumer` value (e.g. `telegram-bot`: the bot relaying the human's approval; `docs/HEADLESS_CHANNEL.md`); `rootmark promote`/`demote` write it only if `--source` is given; MCP and a rule's promotion do not write it. HTTP needs `X-Consumer` on every call (§1): a `promote` without the header is refused with 400 as before and writes nothing. The label says not **who** the human is but **through what** they acted (`human_id` stays single). Reading rule: if the field is absent, accept (all logs before 2.0.3); if present, a non-empty string, otherwise the vault is refused when opened. `history` shows the field in the event's `meta`; a client only shows it and does not trust it (it is a declared label).

## 5. Order and determinism (K-D1.4, spec §10)
- Writing and trace-writing calls (`search`, `read_block`, `propose`, `promote`, `checkpoint`; also the watcher and compaction) are processed one by one in a single FIFO queue per vault, **in order of arrival**. The queue belongs to the single `rootmark serve` process (§1). Over MCP the order of arrival is the order in which requests are read from stdio. Over HTTP it is the moment a request is accepted. MCP and HTTP share the same queue.
- A pipelining client (sending without waiting for answers) produces, with the same sequence of requests, the same `events.jsonl`, `traces.jsonl` and md files as a lock-step client. Answers can arrive out of order; the client matches them by `id`.
- A cancelled call (`notifications/cancelled`) still runs at its place of arrival. Cancelling neither undoes nor moves a write.
- Read-only calls (`status`, `history`, `blame`, `checkpoints`, `trace`) run in parallel with each other and wait while a writer runs. A read may not see a write sent before it but not yet processed. A client that wants to see a write's result waits for its answer.

## 6. Version
`status.spec_version` (the spec version, `docs/SPEC_EDITS_CRITERION.md`) and `status.mdk_version`. This contract is P1-D.1's behaviour together with P1-E/E0's two addenda (K-E0.3 `index_stale`, K-E0.4 `hint` and the agent guideline), P1-E.1's `status` addendum (K-E1.2: the `status.index` object, `status` independent of the index, an unreadable manifest `index_stale`), P2-0's attestation addendum (K-P2-0.5: the §2.6 endpoints, `status.attestation`, the `unverified` layer, the shutdown note), P2-0.1's attestation paths addendum (K-P2-01.2: `link_update_of`, `status.attestation.link_updates`; K-P2-01.3: `content`, `link_update_from`, the partial match, CLI `--renamed-from`), P2-0.2's link forms and layer carrying addendum (K-P2-02.2: the Markdown label turning with its target, carrying layers block by block in `renamed_from`, the renamed note's own link update), P2-P's addendum (K-P2P.2: `status.attestation.implicit`, `status.migrations.recommended`/`artifacts.policy`/`error`; K-P2P.1, K-P2P.3: declarative promotion rules §2.1, promotion by a rule §2.4, `demote` §2.7; K-P2P.4: the channel label of a transition §4.2) and P2-A's addendum (K-GH.6: a spelling variant of directory components is `exists` on every platform; K-P2A.2: `status.migrations`, `migration_required`; K-P2A.1: the explicit `unattested = "canonical"` value of `rootmark serve`'s recipe, the check of the renamed note's own late link update against the head of the old path, `--attest-log`) (version 1). **Version 2** (P2-B, K-P2B.1): the block position `loc` and `loc_stale` (§2.5; experimental, K-P2B-T1), the search date filter (§2.2), the event stream `events` (§2.8), the machine-readable response schema (§2.9). Version 2 only adds optional fields and new endpoints; no field, code or behaviour of version 1 changes. **The addendum to version 2** (P2-R, K-P2R.1): retention and pruning `POST /v1/prune` (§2.10), `status.retention`, `checkpoints[].archived`, `trace.archived_before`, the error code `archived` (§3) — only added fields, a new endpoint and a new code; in a vault without an archive every answer is unchanged, and a version 2 client does not break. Changes happen through a decision record (`docs/DECISIONS.md`, development repository) and an update of this document.
